## Merge

- [ ] **Squash-merge to `main`.** `gh pr merge --squash --delete-branch`.
- [ ] **Verify origin post-merge** (per `gh --delete-branch` 3-leg L generalization, chat-9/10): `git ls-remote --heads origin` — should be `main` only. If a survivor branch shows, run `git push origin --delete <branch>` explicitly. Local-delete survivors clear with `git branch -D <branch>`.
- [ ] **Resolve squash-merge divergence locally** if applicable: `git checkout main && git reset --hard origin/main`.
- [ ] Confirm Netlify auto-deploy fires; wait ~30s for build; open the live URL with hard reload (Cmd+Shift+R).

A fail-closed unresolved relation (not reachable from an ordinary calculated pair) shows the `relation layer unavailable` copy plus a `compare another` recovery action and hides the signature/evidence/share controls — never a dead button pointed at nothing.
  - **Pair Imprint** (doctrine §1.J/§5.D v0.81–v0.86; current through the exact-gate remediation, 2026-09-05) — the pre-action disclosure text is truthfully CONDITIONAL, never an unconditional promise, and never claims a completion this module cannot observe: `shares directly when your device supports it, otherwise downloads it as an image` when the platform exposes native share methods, plain `downloads the pair imprint as an image to this device` when it doesn't (method presence alone never implies a share will succeed, and "downloads" describes the action taken, never "saves" — nothing here learns whether the browser wrote the file to disk). The PNG is pre-rendered and cached the instant a resolved relation becomes current (a narrow `onRelationChange` hook from `ui/dyad.js`, invalidated on close/Compare Another/Previous Readings/any replacement, and pinned as executable structure by a dedicated static test) so `navigator.share()` can be called SYNCHRONOUSLY inside the click handler with no prior `await` — required for the Web Share API's transient-activation rule; native share is attempted ONLY when that cached blob is already ready at click time, never after a wait. The share button goes `aria-busy="true"` and disables both while the artifact is being prepared (background pre-render, which persists past 4 seconds if the render genuinely takes that long) and while an active click is in flight. Identity is re-checked after EVERY async boundary (a pending render, `navigator.share()` resolving OR rejecting, `clipboard.writeText()` resolving OR rejecting), but the check means two DIFFERENT things depending on WHEN it fires: **before** any irreversible effect (the render/wait itself), a CONFIRMED pair change reports `stale` and nothing further happens (an UNCONFIRMED read — the hook threw — reports `failed`, never `stale`, since a throw proves no change); **after** an irreversible effect has already completed (a share() call resolved, or a download already fired), a confirmed change OR an unconfirmed read is reported as `shared-selected` / `download-started-selected[-copied]` — truthfully naming the real, completed effect as concerning the pair SELECTED at click time (never "previous pair"), never erased into a false `stale`/`failed`. If the controller itself is retired (a re-init took over the same DOM) while an operation is resolving, nothing is announced at all, on either owner's refs. A missing/throwing `File` constructor, or `navigator` absent entirely, always falls through to the on-device PNG download — never a bare "failed". A non-AbortError share rejection preserves the local download rather than giving up, subject to the same identity recheck every other preparatory boundary uses. **Current mechanism (doctrine v0.86): a model-first, non-recursive view coordinator**, not the earlier per-boundary `stillCurrent`-checkpoint scheme this line used to describe. One canonical desired-view model governs the button's `disabled`/`aria-busy` and the status node's `textContent`/`hidden` for the SAME physical button+status pair (a re-init on the same refs shares the coordinator; partial overlap — same button, different status, or vice versa — is explicitly out of contract). Four distinct monotonic identities are never conflated: which relation notification is latest, which click-triggered operation owns the button, which scheduled terminal timer is still authorized to fire, and which desired-view revision is newest. A transition never reads the live DOM to decide what to write; a single non-recursive drain loop is the only code that ever touches those four DOM fields, so a hostile setter reentering mid-write (e.g. a same-refs reinit) marks the model dirty and returns, and the one active loop reapplies the newest state before returning — proven for a finite depth-5000 synchronous cascade, with no promise of convergence against an adversary that reenters on every call forever. A terminal auto-hide timer arms only if the exact revision that requested it still owns the coordinator once reconciliation settles, so a stale predecessor superseded mid-reconciliation installs no timer of its own. A transient host-setter exception (including a `setAttribute` getter that merely throws rather than being absent) marks that pass failed and retries, bounded, on the unchanged view — it can never surface as `failed` once a share or download has genuinely already fired. The capability-disclosure text write carries its own small, independent reassertion mechanism against the same same-refs-reinit hazard, kept deliberately separate from the four-field coordinator above. Each `initPairShareUI()` call is still isolated in its own controller object; a re-init retires the prior controller so its in-flight completion can never write into new refs or admit a third click. The constructed snapshot never carries a name, DOB, birth time, timezone, latitude, longitude, city, either raw sheet, or written card text — only the three allow-listed relation summaries plus fixed copy — and the three signature values are geometry-fitted so the longest real line (enumerated from the actual content tables) never overflows its text lane.

## If something fails

- CI red → fix the cause; do not bypass.
- Local audit red → fix per `audits/LOCAL_PII_AUDIT.md` "what to do if you find a leak."
- Live URL broken → roll back via Netlify dashboard (instant); diagnose offline.
- Surface lands wrong but functional → file an `x.y.z` follow-up note in `journal.md`; hotfix release if §4 / §5 / §11 violation, otherwise surface-polish cycle.
- Post-merge audit surfaces P0/P1 → absorb in follow-up PR or hotfix release. v0.3.0.1 / v0.3.0.2 are the canonical pattern: cherry-pick onto a fresh branch from `main` per L48 / L27. Do NOT push direct-to-main for post-merge defect closure.
