## What this override does not cover

Unlike #132, which shipped no product code, this changes CI behavior. The
risk is not in the runtime; it is in the gate, and a gate fails in a way
that is hard to see.

- **The dangerous direction is the silent one.** If the guard is wrong in
  the strict direction — `ADDED` under-resolving, so a legitimate artifact
  is not matched — the result is a visible red on an honest PR: annoying,
  self-announcing, fixable. If it is wrong in the loose direction — `ADDED`
  effectively equalling `CHANGED` on the runner, so the guard closes
  nothing — the result is a gate that looks exactly like a working gate.
  Nothing fails. This PR's own red proves the strict path executes; it does
  **not** prove the guard would actually catch a recycled artifact on a real
  PR, because no such PR has existed. That case was verified only by local
  simulation, by the lane that wrote it.

- **A legitimate workflow this newly forbids.** An artifact that already
  exists on the base branch and is *amended* by a PR no longer satisfies the
  gate — only a genuine addition does. That is the intent, but it is a
  behavior change no second party has weighed, and it will present as an
  inexplicable red to whoever hits it first.

- **Rename and copy detection is environment-coupled.** `--find-renames`
  and `--find-copies-harder` depend on git's similarity heuristics and
  version (runner: 2.54.0). Local simulation and the runner agreed here,
  but the guard's behavior on a large or unusual diff is unverified, and
  `--find-copies-harder` is the expensive option.

- **The test is same-lane.** `tests/l48_gate.test.js` gains four assertions
  pinning the guard, written by the author of the guard, in the same PR.
  It proves the shipped workflow says what this PR claims; it cannot
  independently judge whether the accept/reject set is the one doctrine
  intends.

- **The scope note is prose, not enforcement.** The workflow comment states
  that this does not close #126's F1 on its own — that the shape predicate
  is what rejects a renamed record, and this closes only the adjacent
  recycling dodge. A test asserts the comment is present. Nothing asserts
  the claim is true; it rests on the analysis in the PR body and on
  `git diff --name-status origin/main...HEAD` showing `A`, not `R`, for the
  #126 case.

- **Scope:** this override covers **#133 only**.

## Standing gap, unchanged by this PR

Nothing yet blocks a merge on a red check. Branch protection requiring
`test` and `l48-gate` is repo-admin and is not set. This file records a
choice that was made, not a constraint that had to be lifted.

**One adjacent finding, surfaced while retargeting this PR and not fixed
here.** `ci.yml` declares `on: pull_request:` with no `types:`, so it
defaults to `opened`/`synchronize`/`reopened`. Retargeting a PR fires
`edited`, which is not in that set — so a retargeted PR draws **no checks
at all**, and an absent check is visually indistinguishable from a pending
one. #133 sat at zero checks until a close/reopen forced a run. If these
contexts are ever made required under branch protection, a retargeted PR
would block indefinitely with no signal. Closing it means adding `edited`
to the trigger's `types:`; that is a further CI change and was deliberately
not bundled into this one.
