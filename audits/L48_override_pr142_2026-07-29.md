## What this override does not cover

- **The change cannot be exercised by its own PR, and was not.** Every
  check on #142 fired on `opened` — an action that was never broken.
  Nothing here tests `edited`. No retarget was performed on this PR or any
  other to observe the fixed behavior. The fix rests on GitHub's documented
  action list plus the #133 incident being consistent with it. That is a
  reasonable basis and it is not an observation.

- **When it takes effect is genuinely unknown to this lane.** For
  `pull_request` events GitHub resolves the workflow from the PR's merge
  commit, which would mean #142 covers itself; the trigger *registration*
  may instead be read from the base branch, which would mean it covers
  nothing until merged. This lane did not determine which. The unambiguous
  case is "after this merges to `main`." Anyone relying on it before then
  should verify rather than assume.

- **The load-bearing premise has never been observed in this repo.** The
  entire no-guard argument rests on: *a skipped job can satisfy a required
  status check*. That is GitHub-documented, and it is why a narrowing `if:`
  would be a false-green rather than a refinement. But branch protection is
  not enabled here, so no required check has ever existed to test it
  against. If that premise is wrong, the guard was the better design and
  this PR deliberately chose the worse one. The decision is a judgment
  about a mechanism this repo has never actually run.

- **`edited` is broader than "retarget."** Title and body edits now start
  both jobs. The inline comment says so and accepts the cost. What it does
  **not** say: editing a **closed or merged** PR's body also fires `edited`,
  so both jobs will now run against closed PRs. Harmless, wasteful, and
  undocumented in the workflow — recorded here so it is not discovered as a
  surprise.

- **No `concurrency:` group was added.** Rapid successive edits now queue
  duplicate full runs with nothing cancelling the superseded ones. Adding
  one is the obvious companion change and was deliberately not bundled —
  `cancel-in-progress` introduces its own failure surface around cancelled
  checks, which deserves its own PR rather than a rider on this one.

- **One test pin is broader than its stated rationale.** `carries no
  job-level `if:`` forbids **every** job-level `if:` in this workflow, not
  merely a types-narrowing guard. A future job with a legitimate job-level
  condition will fail the suite and be met with a message about
  skipped-checks that may not apply to its case. The over-tightness is
  intentional — a narrow pin would be easy to route around — but the test's
  own comment does not admit that it over-reaches, and a future reader will
  have to work that out from here.

- **The tests read YAML; they do not execute it.** They pin
  *configuration*, not behavior: they prove the workflow declares `edited`,
  never that GitHub acts on the declaration. Same-lane, same PR, written by
  the author of the change.

- **What is genuinely reassuring, so the balance is honest.** Before
  committing, `ci.yml` was mutated four ways and each mutation killed
  exactly one intended test and no others — drop `edited`, drop
  `synchronize`, remove the `types:` line, add a job-level `if:`. None of
  the four pins passes vacuously, which is more than can be said for most
  of the source-reading tests in this repo. Separately, #142 drawing both
  jobs on `opened` is a live confirmation that declaring `types:` did not
  break the defaults — the one way this change could have caused the exact
  outage it fixes. And it is one functional line, trivially revertible.

- **Scope:** this override covers **#142 only**.

## Standing gap, and why this PR is a precondition for closing it

Nothing yet blocks a merge on a red check. Branch protection requiring
`test` and `l48-gate` is repo-admin and is not set. This file records a
choice that was made, not a constraint that had to be lifted — the fifth
consecutive sighting to say so.

Worth stating in the affirmative for once: **this PR is a prerequisite for
ever turning that protection on.** Under required contexts, a retargeted
PR that draws no checks does not fail — it blocks indefinitely with no
signal and no way to force a run short of close/reopen. #133 experienced
exactly that with protection off, where it read as a puzzling absence. With
protection on it would read as a deadlock. Closing this gap first is what
makes the standing gap closable at all.
