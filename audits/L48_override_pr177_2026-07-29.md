# L48 override — PR #177 cleared on explicit controller word, no cross-lane read

This file is the L48 sighting log by construction (per the gate's own design:
"the override file IS the L48 sighting log"). **Sighting #21.**

- **PR:** #177 — resolves the duplicate sighting numbers on `main` and adds the
  pin that stops them recurring. Renumbers this lane's `L48_override_pr160`
  from #17 to #19, updates its three references, and adds two tests to
  `tests/l48_gate.test.js`. Four files.

- **The ledger fix is cleared by an entry in the ledger it fixes.** Same
  recursion as the gate governing its own modification (#98, #122, #133, #160
  — sighting #19 records that pattern), one level further in: a PR that makes
  sighting numbers unique needs a sighting number, and gets it under the very
  scheme it is repairing. Recorded rather than left as a curiosity, because the
  repo keeps producing this shape and each instance has so far cleared by
  override rather than by a read.

- **The change does verify itself, in the one narrow sense available.** The pin
  added by this PR reads every override in `audits/` and asserts each number is
  claimed exactly once — including this file. If #21 were already taken, this
  PR's own `test` job would go red. That is a real check and it is not a
  substitute for review: it proves the number is unique, not that renumbering
  `pr160` rather than `pr168` was the right call.

- **State at the word:** `test` green — 45 files / 1585 tests, +2 from this
  PR's own new pins. `l48-gate` red solely for want of this file. Ledger on
  this branch: #6, #8–#19, no duplicates, verified by direct enumeration.

- **Cross-lane read: none.** None run, none commissioned, none in flight. The
  auditor lane remains vacant (sighting #14; §10 amendment drafted in #166 and
  still a draft), and the lane-neutral packet shipped in #172 has not been run
  by anyone.

- **Word:** explicit in-session controller instruction — *"write the override
  for pr177"*. Controller override authority per DOCTRINE §10/§14.

- **What this override does not cover.** Two judgment calls in this PR are
  unreviewed, and neither is mechanical:

  1. **Which record moved.** `pr160` landed 20 seconds before `pr168`, so by
     seniority `pr168` should have renumbered. This lane moved its own record
     instead, on the grounds that `pr168`'s #17 is cited in `DOCTRINE.md`'s
     v0.59 footer and renumbering it would require a doctrine amendment that
     §10 cannot currently review. That reasoning is defensible and it is also
     self-serving in a way worth naming: the lane that chose was the lane that
     would otherwise have had to touch another lane's merged record. A reviewer
     might reasonably say the constitution should have been corrected instead.
  2. **Uniqueness pinned, contiguity and ordering not.** The consequence is
     that the numbers are now identifiers rather than a sequence — `pr160`'s
     sighting occurred first and carries the higher number. That is a permanent
     property of the ledger from here, decided by one lane in one PR.

- **Ledger note, which this file makes worse.** This is the twelfth override on
  a ledger of twenty-one sightings. The #159 audit's ledger lens raised the
  trend — the override is the default path, not the exception — and every entry
  filed since has continued it, including this one and including the entries
  that exist to record the trend. Nothing here breaks that; it is one more
  observation for the controller.

- **Standing gap, unchanged.** A red check still does not block a merge; branch
  protection requiring `test` and `l48-gate` is repo-admin and unset. So the
  new uniqueness pin, like the gate it lives beside, is enforced by convention
  rather than by anything mechanical.
